# 1 Oauth与JWT的关系

| 步骤 | 动作                                               | **OAuth 2.0 的职责**                                   | **JWT 的职责**                                      |
| :--- | :------------------------------------------------- | :----------------------------------------------------- | :-------------------------------------------------- |
| 1    | 客户端发来用户名/密码                              | 定义“用凭证换令牌”这个**接口规范**                     | （尚未出现）                                        |
| 2    | auth服务验证通过，返回令牌                         | 定义“返回的必须包含 `access_token` 和 `refresh_token`” | 实际返回的 `access_token` 就是 **JWT 格式**的字符串 |
| 3    | 客户端携带 `Authorization: Bearer {token}` 请求API | 定义了 `Bearer` 这种**传递令牌的方式**                 | 网关解析这个字符串，校验**签名**和**有效期**        |
| 4    | 24小时后令牌过期                                   | 定义“必须用 `refresh_token` 重新申请”的**刷新流程**    | 旧的 JWT 失效，auth 服务签发**新的 JWT**            |



# 2 Auth服务与网关



| 层级                       | 职责         | **做什么**                                                   | **不做什么**                                                 |
| :------------------------- | :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **Auth 服务（独立）**      | **发证机关** | 验证用户名/密码、签发JWT、颁发刷新令牌、管理SSO会话。        | 不处理业务API请求，不校验业务权限（如“这个订单是不是这个用户的”）。 |
| **API 网关（统一关卡）**   | **门卫**     | **校验JWT签名**、**校验有效期**、提取用户身份（如 `user_id`）并转发给下游。对未认证请求直接返回 **401**。 | 不做复杂的业务逻辑判断（如查询数据库判断用户等级）。         |
| **业务微服务（具体应用）** | **业务员**   | 接收网关已校验过的请求，**仅校验“业务权限”**（如：RBAC中的角色、数据范围）。 | **不再重复校验JWT签名**，不调用Auth服务查Token状态（因为网关已做）。 |

```text
│      │              │  职责：验签  │

                      └──────┬──────┘                    │

                      ┌─────────────┐                    │

```

# 3 X-User-Id

具体业务怎么根据X-user-Id去拿用户的权限信息？

这个问题问到了**权限体系设计**的核心。你注意到没有——网关只负责**认证（Authentication，确认你是谁）**，但**授权（Authorization，确认你能干什么）**必须由业务系统自己决定。

而 **`X-User-Id` 只是钥匙，不是地图**。业务服务需要拿着这把钥匙，去查找这个用户对应的“权限地图”。

我分**三种主流方案**给你讲解，从简单到复杂，你可以根据业务规模选择。

### 方案一：本地缓存 + 定时同步（中小规模，性能最优）

**核心思路**：业务服务启动时，从权限中心（或Auth服务）全量拉取所有用户的权限数据，缓存在本地内存，定时（如每分钟）增量同步。

```text
┌────────────┐  1. 请求携带 X-User-Id   ┌────────────┐
│   API网关  │ ────────────────────────▶│  订单服务   │
└────────────┘                           └──────┬─────┘
                                                │
                                                ▼
                                        2. 从本地缓存中
                                           查 UserId=123
                                           的权限列表
                                        (Redis/本地Map)
                                                │
                                                ▼
                                        3. 判断是否有
                                          "order:delete" 权限
```

### 方案二：Redis 集中缓存（主流中大型项目）

**核心思路**：权限数据集中存储在 Redis，业务服务每次请求都去 Redis 查询该用户的权限。Redis 设置合理过期时间（如 30分钟），权限变更时主动失效。

```text
┌────────────┐  1. X-User-Id   ┌────────────┐
│   API网关  │ ───────────────▶│  订单服务   │
└────────────┘                  └──────┬─────┘
                                       │
                                       ▼
                               2. 查询Redis
                           Key: "perm:user:123"
                           Value: ["order:read", "order:delete"]
                                       │
                                       ▼
                               3. 命中则返回
                                  未命中则查DB并回填
```

### 方案三：JWT 自带权限（极致性能，但需谨慎）

**核心思路**：在签发 JWT 时，直接把用户的**权限列表**（或角色）写入 JWT 的 Payload 中。业务服务解析 JWT（网关已验签，业务服务只需解码 Base64）即可拿到权限，**零网络开销**。

```text
// JWT Payload 示例
{
  "user_id": "123",
  "roles": ["admin", "operator"],
  "permissions": ["order:read", "order:delete", "product:create"],
  "exp": 1718000000
}
```

### 方案四：网关透传 + 业务服务按需查询（最灵活）

**这是你当前架构的升级版**——网关不仅透传 `X-User-Id`，还透传网关从 JWT 中解析出的 **`X-User-Roles`**（角色列表）。业务服务拿到角色后，再根据**本地配置的角色-权限映射表**（而不是查数据库）来判断权限。

# 4 权限体系

在权限管理领域，**ACL**，**RBAC** 和 **ABAC** 是三种最核心的模型。它们不是互斥的，而是从“粗放”到“精细”的演进关系。

为了让你直观理解，我先用**公司门禁系统**打个比方，再展开技术细节：

-   **ACL（访问控制列表）**：像是**门卫手里的名单**。名单上写着“张三能进机房，李四能进财务室”。它直接告诉**“谁”**能**“做什么”**。
-   **RBAC（基于角色的访问控制）**：像是**公司的职位工牌**。你戴上“技术总监”的工牌，就自动拥有技术部所有权限。它通过**“角色”**这个中间层，把权限分配给**“一类人”**。
-   **ABAC（基于属性的访问控制）**：像是**智能安检系统**。它不看你的名字，也不看你的职位，而是看**“你是谁（部门）”、“什么时间（上班时间）”、“用什么设备（公司电脑）”、“要查什么数据（自己部门的）”**，综合所有条件动态决定是否放行。

---

## 1. ACL

访问控制列表（Access Control List）

这是最传统、最直接的模型。

-   **核心思想**：**“谁”** 对 **“哪个资源”** 有 **“什么权限”**。
-   **数据结构**：它是一个扁平的列表，直接把权限挂在用户或资源上。
-   **优点**：简单直接，实现成本低。
-   **缺点**：**管理灾难**。如果公司有1000个人和100个文件夹，管理员需要手动配置数万条关系。一旦人员变动（调岗/离职），维护成本极高。
-   **典型场景**：老旧系统的文件权限（如Windows早期文件共享）、简单的硬件防火墙规则。

---

## 2. RBAC

基于角色的访问控制（Role-Based Access Control）

这是目前**最主流、最通用**的企业级权限模型（比如大多数后台管理系统）。

-   **核心思想**：**“用户”** 关联 **“角色”**，**“角色”** 关联 **“权限”**。
-   **数据逻辑**：用户 → 角色 → 权限。
-   **优点**：**极大简化管理**。你不需要给100个人分别授权，只需维护“财务经理”、“运维工程师”等几十个角色的权限。新员工入职，只需给他分配一个角色即可。
-   **缺点**：**灵活性不足**。如果“技术总监”今天下午3点需要临时查看财务数据，你只能给他创建一个临时角色，或者修改他的角色，用完再改回来，非常麻烦（这被称为“角色爆炸”）。
-   **典型场景**：OA系统、ERP系统、公司内部管理后台。

---

## 3. ABAC

基于属性的访问控制（Attribute-Based Access Control）

这是目前**最灵活、最细粒度**的模型，也是云原生和零信任架构的首选。

-   **核心思想**：它不依赖固定的角色，而是通过一组**动态属性**来判定权限。
-   **判定逻辑**：权限 = **主体属性**（用户年龄、部门、职级）+ **客体属性**（数据密级、创建人）+ **环境属性**（当前时间、IP地址、设备安全状态）。
-   **优点**：**动态且精细**。例如，规则可以设置为：“**只有**（**本部门** 的 **正式员工**），在 **工作时间** 内，使用 **公司内网**，才允许 **编辑** 属于 **自己团队** 的 **项目文档**”。
-   **缺点**：**实现复杂**，性能开销大（因为每次请求都要实时计算），且策略一旦过多，管理难度极高（需要配合可视化策略引擎）。
-   **典型场景**：AWS/IaaS云平台资源管理、大型金融系统、医疗数据脱敏访问。

---

## 总结对比表

| 维度         | **ACL**                                  | **RBAC**                         | **ABAC**                                     |
| :----------- | :--------------------------------------- | :------------------------------- | :------------------------------------------- |
| **授权粒度** | 粗粒度（资源级）                         | 中粒度（功能/菜单级）            | **细粒度**（数据/字段级）                    |
| **管理成本** | **极高**（关系爆炸）                     | **低**（只需维护角色）           | 中等（需维护策略规则）                       |
| **动态性**   | 静态绑定                                 | 静态绑定                         | **动态计算**（实时生效）                     |
| **复杂度**   | 低                                       | 中                               | **高**（需规则引擎）                         |
| **典型问题** | “张三离职了，谁帮他把所有文件权限收回？” | “临时授权怎么办？只能新建角色。” | “谁写了这条规则？为什么昨天能访问今天不能？” |

---

## 现实中的组合拳（扩展知识）

在实际大型系统中，三者往往是**混合使用**的：

1.  先用 **RBAC** 做粗筛（比如：只有“管理员”角色才能进入后台）。
2.  在具体数据查询时，再叠加 **ABAC** 做精滤（比如：虽然是管理员，但只能看“华东区”且“未归档”的订单数据）。
3.  而底层的数据库表或微服务接口，则通过 **ACL** 做基础的访问拦截。

如果你现在要设计一个权限系统，我建议：**常规业务用RBAC就足够了**；只有当业务涉及“多维度数据隔离”（如多租户、跨区域、敏感字段脱敏）时，才需要考虑引入ABAC。
